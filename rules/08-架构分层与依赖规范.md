# 架构分层与依赖规范

## 1. 核心约束
- 高内聚：同一业务域的代码（实体、逻辑、接口、模型）聚集在同一模块内
- 低耦合：模块间通过接口或事件通信，禁止直接引用其他模块内部实现
- 单向依赖：依赖只能从外层指向内层，禁止反向依赖和循环依赖

## 2. 层间依赖方向（Clean Architecture）

```
外层 ──依赖──▶ 内层（只能单方向，禁止反向）

API（控制器/路由）
  │
  ▼
Application（用例/DTO/接口定义）
  │
  ▼
Domain（实体/值对象/领域事件）  ◀── 核心层，零外部依赖
  │
  ▲
Infrastructure（数据库/MQ/第三方API）
  │
  ▲
外部框架、SDK、中间件
```

### 各层依赖规则

| 层 | 可以依赖 | 禁止依赖 |
|----|----------|----------|
| Domain | 无（零外部依赖） | Application、Infrastructure、API、任何框架 |
| Application | Domain | Infrastructure、API、任何框架具体实现 |
| Infrastructure | Domain、Application（仅接口） | API |
| API | Application、Domain（仅DTO/枚举） | Infrastructure |

### 依赖倒置原则
- Application 层定义接口（如 `IUserRepository`、`IMessageSender`）
- Infrastructure 层提供实现（如 `UserRepositoryImpl`、`RabbitMQMessageSender`）
- 通过依赖注入容器在启动时绑定，运行时 Infrastructure 实现注入 Application

### 接口归属约定
> 接口定义放 Application 还是 Domain，是 DDD 实践中的常见分歧点。本规范统一约定如下，避免团队各自理解：

- **仓储接口（`IUserRepository` 等）归属 Domain 层**：持久化是领域关注点，接口语义属于领域。Domain 依赖自己的接口定义，但不依赖任何实现，仍保持零外部依赖。
- **外部服务接口（`IMessageSender`、`IPaymentGateway` 等）归属 Application 层**：这些是应用编排关注点，不属于核心领域语义。
- **判定原则**：接口描述的是"领域数据的持久化"→ Domain；接口描述的是"应用与外部世界的交互"→ Application。
- Infrastructure 层实现上述两层接口，通过 DI 绑定，不改变归属层。

## 3. 模块间通信规则

### 同层模块间
- 禁止跨模块直接 import 其他模块的内部类/函数/变量
- 必须通过以下两种方式通信：
  1. **接口调用**：模块对外暴露公共接口/服务，其他模块通过接口引用
  2. **事件/消息**：模块发布领域事件，其他模块订阅处理，实现解耦

### 跨层模块间
- 上层调用下层：通过接口注入，正常调用
- 下层通知上层：通过领域事件、回调接口，禁止反向引用

### 示例（正确 vs 错误）

```
✅ 正确：
  OrderModule 发布 OrderCreatedEvent
  InventoryModule 订阅 OrderCreatedEvent 扣减库存
  （两个模块互不感知，通过事件解耦）

❌ 错误：
  OrderModule 直接 import InventoryModule 的 InventoryService 调用扣减库存
  （模块间强耦合，Inventory 变更直接影响 Order）
```

### 事件通信可靠性约束
> 事件解耦带来灵活性的同时引入最终一致性、重复消费、调试困难等成本。通过事件通信时必须满足以下约束：

- **幂等性**：订阅方处理逻辑必须幂等，同一事件重复投递不得产生副作用（如重复扣减库存）。通过业务唯一键或事件 ID 去重。
- **补偿机制**：事件处理失败必须有补偿策略——重试、死信队列、人工介入兜底，禁止"失败即丢弃"。关键业务事件必须配死信队列 + 告警。
- **事件版本化**：事件结构变更必须版本化（如 `OrderCreatedEventV2`），保证旧订阅方在升级期间仍可消费。
- **可追踪**：每个事件必须携带 traceId / correlationId，链路追踪系统可串联发布方与所有订阅方，解决"事件断了难追"问题。
- **事务边界**：发布事件与业务操作不在同一事务时，必须使用事务发件箱（Outbox Pattern）或本地消息表，禁止"先提交事务再发事件"导致的不一致。

## 4. 循环依赖禁令

### 禁止任何形式的循环依赖
- A 依赖 B，B 依赖 A → 禁止
- A → B → C → A → 禁止
- 模块级循环、文件级循环、类级循环全部禁止

### 发现循环依赖的解决方式

| 场景 | 解决方案 |
|------|----------|
| 两个模块互相调用 | 提取公共接口到上层或 shared 层，双方依赖接口 |
| 两个类互相引用 | 引入中间类/事件/回调接口打破循环 |
| 模块A需要模块B的部分功能 | 将该功能提取为独立公共模块 |

### CI检测
CI流水线中集成循环依赖检测工具，发现循环依赖直接构建失败：
- .NET：`dotnet-depends` 或 ArchUnit
- Java：ArchUnit
- Go：`go vet` + 自定义依赖分析脚本
- 前端/Node：`dependency-cruiser`、`madge`

## 5. 共享代码边界

### 允许放入 shared/common 的内容
- 跨 3 个以上模块使用的纯工具函数（日期、加密、格式转换）
- 全局枚举、常量（状态码、业务类型定义）
- 统一返回体、全局异常基类
- 跨模块共享的 DTO/类型定义（前后端共享场景）

### 禁止放入 shared/common 的内容
- 任何包含业务逻辑的代码（业务逻辑必须在对应业务模块内）
- 只被 1-2 个模块使用的代码（就近放在使用方模块内）
- 对特定框架/中间件的封装（放在 Infrastructure 层）

### 判定规则
```
一个函数/类该放哪里？

只被1个模块用 ──▶ 放在该模块内部
被2个模块用 ──▶ 放在调用方模块，被调用方暴露接口
被3个以上模块用 ──▶ 提取到 shared/common
包含业务逻辑 ──▶ 永远不放 shared，归属对应业务模块
```

## 6. 前端分层依赖规则

| 层 | 内容 | 可依赖 | 禁止依赖 |
|----|------|--------|----------|
| components/ | 全局公共UI组件 | utils、common、assets | modules、api |
| modules/业务模块 | 页面、组件、hooks、store | api、utils、common、components | 其他 modules |
| api/ | 接口封装、拦截器 | utils、common、config | modules、components |
| store/ | 全局状态 | api、utils、common | modules、components |
| utils/ | 纯工具函数 | 无（零依赖） | 所有其他层 |

### 模块间禁止直接引用
```
✅ 正确：
  modules/user 通过 api/userApi 获取数据
  modules/order 通过 api/orderApi 获取数据

❌ 错误：
  modules/order 直接 import modules/user 的 useUserStore 获取用户信息
  （应通过 api 层或 shared store 获取）
```

### 跨模块只读引用豁免
> 完全禁止跨模块引用在实操中摩擦较大——订单页展示用户名这类场景太常见，强行绕 api 层多一次网络请求不划算。区分读写：

- **读操作允许**：模块可对外暴露只读 selector / getter（如 `useUserName(userId)`、`getUserName(id)`），其他模块可引用这些封装好的只读接口获取数据。封装函数内部不得暴露可变状态或写入方法。
- **写操作禁止**：禁止跨模块调用另一个模块的 mutation / action / setState，状态变更必须归属原模块。
- **暴露形式约束**：只读 selector 必须封装在模块的 `public/` 或 `index.ts` 公共出口中，禁止直接 import 模块内部的 store / state 文件。

## 7. 桌面应用分层依赖规则

| 层 | 可依赖 | 禁止依赖 |
|----|--------|----------|
| Core（纯业务逻辑） | 无外部依赖 | UI、Services、Infrastructure |
| Services（网络/文件/硬件） | Core（通过接口） | UI |
| Infrastructure（本地存储） | Core（通过接口） | UI、Services |
| UI（视图/ViewModel） | Core、Services、Infrastructure | - |

Core 层必须做到：脱离 UI 框架可以独立运行和测试。

## 8. 分层豁免判定

> 强制四层对简单 CRUD 实体是无意义透传，但不加约束的豁免会让规范形同虚设。本节定义可审计、可判定的豁免标准：四个硬信号全部不命中才可豁免，任一命中必须完整四层。

### 四个硬信号（任一命中 = 必须四层）

| 信号 | 判定标准 | 命中示例 |
|------|----------|----------|
| ① 业务不变量 | 实体内部存在必须永远成立的跨字段约束规则 | 订单总额 = 明细之和；审批状态不可逆流；积分不可为负 |
| ② 状态机 | 实体有多于 2 个状态，且状态间有迁移规则（非单纯软删标记） | 草稿 → 待审 → 已通过 → 已发布，不可跳过待审 |
| ③ 跨实体协调 | 操作此实体时需校验或联动其他实体 | 建订单校验库存；审批查权限；扣款联动账户余额 |
| ④ 领域事件 | 其他模块需响应此实体的变更 | 订单创建后库存扣减；用户注册后营销发券 |

### 豁免条件
四个信号全部不命中时，方可申请分层豁免。典型豁免实体：系统配置表、字典表、操作日志、简单标签管理。

### 豁免后的合并方式
豁免不是"不分层"，而是"用一套通用四层实现服务多个简单实体"，架构仍分层：

- **Domain 层**：不单独建，实体为纯数据结构（struct / record / POJO）
- **Application 层**：使用通用 Repository 接口 + 通用 CRUD 用例，不写专用 UseCase
- **Infrastructure 层**：一个泛型 Repository 实现服务所有豁免实体
- **API 层**：Controller 直接调用通用用例

### 豁免留痕规则（防止滥用）
豁免必须在代码中留痕，code review 时对照审查：

```
// @layering:exempt reason=no-invariants,no-state-machine,no-coordination,no-events
// 审查人：xxx  日期：YYYY-MM-DD
```

- 留痕注释放在实体类或模块入口文件顶部
- 后续实体演进出现任一硬信号时，必须升级回完整四层并移除豁免标记
- Code review 必查：豁免理由是否仍成立、四个信号是否确实全部不命中

## 9. 依赖检查清单（Code Review 必查项）

- [ ] Domain 层无任何外部框架 import（无 ORM 注解、无 HTTP 类、无 UI 引用）
- [ ] Application 层不引用 Infrastructure 具体实现类
- [ ] 仓储接口归属 Domain 层，外部服务接口归属 Application 层
- [ ] 模块间无直接 import 其他模块的内部文件
- [ ] 无循环依赖（CI工具检测通过）
- [ ] shared/common 中无业务逻辑代码
- [ ] 前端模块间无跨模块直接引用（读操作可通过 public 只读 selector）
- [ ] 前端跨模块写操作禁止直接调用其他模块的 mutation / action
- [ ] 事件通信订阅方幂等、配补偿机制、携带 traceId
- [ ] 桌面应用 Core 层无 UI 框架依赖
- [ ] 分层豁免已留痕，理由成立且四信号全部不命中
